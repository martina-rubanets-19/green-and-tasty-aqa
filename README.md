## Чому публічний сайт

Власний застосунок розгорнути не вдалося. AWS-акаунт, який був у моєму розпорядженні, входить в AWS Organization, і її Service Control Policy явно забороняє створювати ресурси (`s3:CreateBucket`, `sqs:CreateQueue` → `explicit deny in a service control policy`), тож ні Terraform, ні Syndicate не можуть нічого створити. За таблицею з ДЗ («Нічого не розгорнуто») обрано **Напрям 2 на аналогічному публічному сайті**.

**Чому саме цей сайт:**
- його призначення — практика автоматизації, тож автотести тут дозволені й очікувані (на відміну від Booking/Airbnb/OpenTable, де діє захист від ботів і заборона автоматизації в умовах використання);
- предметна область найближча до ресторану: номери з цінами (замість страв), бронювання на дати, форма з правилами валідації, вхід;
- код сайту відкритий ([GitHub](https://github.com/mwinteringham/restful-booker-platform)), тож правила валідації взято з його контракту, а не вгадано.

## Архітектура

```
src/
  config/env.ts        налаштування з .env або змінних середовища
  data/factories.ts    генератори даних: унікальний тег на тест, рядки потрібної довжини, дати відносно «сьогодні»
  api/SiteApi.ts       API-клієнт: підготовка/перевірка стану та прибирання (не замість UI у сценаріях)
  pages/               Page Objects: локатори + дії + перевірки рівня сторінки
    HomePage.ts        головна: номери (RoomCard), пошук вільних номерів, форма контакту (ContactForm)
    RoomPage.ts        сторінка номера /reservation/{id}
    AdminLoginPage.ts  вхід /admin
  fixtures.ts          Playwright fixtures: сторінки, API, автоприбирання тестових даних
tests/
  level1/*.spec.ts     наскрізні UI-сценарії (+ кілька API-перевірок того самого функціоналу)
  api/*.spec.ts        контракт валідації форми на рівні API
```

**Чому POM + fixtures, а не BDD + Screenplay.** Це один із варіантів, дозволених у ДЗ («будь-який інший підхід, який ви можете обґрунтувати»). Для сайту з трьома сторінками Page Object дає ту саму ізоляцію локаторів, що й Screenplay, але з меншою кількістю шарів. Fixtures Playwright замінюють «здібності» акторів (браузер, API) і забезпечують прибирання після кожного тесту. Таблиці граничних значень записані як масиви випадків (data-driven), тож кожен рядок стає окремим тестом зі зрозумілою назвою.

**Локатори** обрано за пріоритетом: роль + доступне ім'я (`getByRole('button', { name: 'Submit' })`), label (`getByLabel('Username')`), test id (`getByTestId('ContactName')`), і лише там, де сайт не дає нічого іншого (картки номерів, поля date picker), — CSS.

## Тестові дані та незалежність

- Кожен тест генерує **унікальні дані** (тег `AQA<uuid>` в імені й темі повідомлення), тож паралельні запуски не заважають один одному.
- **Прибирання:** fixture `messageCleanup` після тесту входить через API адміністратора і видаляє всі повідомлення з тегом цього тесту. Без облікових даних адміна прибирання пропускається, але дані однаково унікальні. Крім того, демо-сайт сам періодично скидає свої дані.
- **Дати** завжди відносні (`сьогодні + 120 днів`), тож тести не застарівають.
- Тести **не залежать від порядку** і запускаються повністю паралельно (`fullyParallel: true`).

## Налаштування

Потрібен Node.js 20.12+ (рекомендовано 22).

```bash
npm install
npx playwright install chromium
cp .env.example .env     # заповнити ADMIN_USERNAME / ADMIN_PASSWORD
```

| Змінна | Значення |
|---|---|
| `UI_URL` | адреса сайту, за замовчуванням `https://automationintesting.online` |
| `ADMIN_USERNAME`, `ADMIN_PASSWORD` | обліковий запис адміністратора сайту. Демо-дані опубліковані на самому сайті, але в репозиторії їх немає. Без них тести успішного входу пропускаються (`skipped`), прибирання вимикається |

`.env` у `.gitignore` — його не комітимо.

## Запуск

```bash
npx playwright test                 # усе
npx playwright test --grep @smoke   # швидкий smoke (4 тести)
npx playwright test --grep @ui      # лише UI
npx playwright test --grep @api     # лише API
npx playwright test --grep @level1  # рівень 1
npx playwright test --grep @negative
npx playwright test --grep "@contact|@login"
npx playwright test tests/level1/rooms.spec.ts
npx playwright test --headed        # з видимим браузером
```

**Теги:** `@level1`, `@ui`, `@api`, `@smoke`, `@negative`, `@boundary-valid`, `@contact`, `@login`, `@rooms`, `@filter`.

## CI (GitHub Actions)

Workflow `.github/workflows/e2e.yml`:
- запускається на push у `main`, на pull request, щоночі та вручну (**Actions → E2E tests → Run workflow**, з полем `grep` для запуску підмножини, наприклад `@smoke`);
- **впалий тест не зупиняє пайплайн** (`continue-on-error`): звіт публікується завжди;
- артефакти запуску: `playwright-html-report` (HTML-звіт) і `failed-test-artifacts` (trace, скриншоти, відео впалих тестів); підсумок тестів показується у вкладці *Checks*.

Налаштування в репозиторії: **Settings → Secrets and variables → Actions**
- Secrets: `ADMIN_USERNAME`, `ADMIN_PASSWORD`
- Variables (необов'язково): `UI_URL`

## Поведінка сайту, зафіксована тестами

- **Номер, якого не існує.** Сервіс номерів відповідає `404` з порожнім тілом, а проксі сайту не може його розібрати й повертає `500`. Сторінка `/reservation/{id}` не показує даних номера (клієнтська помилка рендеру). Тест перевіряє, що деталі номера **не показуються** і API **не відповідає успіхом**, але не прив'язується до конкретного коду (`404` vs `500`), бо поточний `500` — дефект сайту.
- **Форма контакту** не перевіряє дані в браузері: усі помилки приходять із сервера одним блоком `.alert-danger` (по рядку на правило).
- **Головна сторінка** показує не більше трьох номерів, тож тести порівнюють UI з першими трьома номерами з API.
